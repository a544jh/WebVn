# Known rough edges

Real issues that actively confuse new contributors. If you touch the area, consider fixing rather than working around.

- **Dead code paths:** `animations.css` has unused keyframes.
- **Asset loaders have no error handling.** A single broken image rejects `ImageAssetLoaderSrc.loadAll`. Audio waits for `canplaythrough` with no error listener — a broken audio file hangs startup.
- **Duplicated bootstrap between `src/index.ts` and `src/playerIndex.ts`.** The demo script and its actor/asset state now live in `src/demoStory.ts` and both entry points import it, but the fullscreen listener, `setScale` and `restoreOnFullscreenExit` are still copied verbatim into both. If you fix one, fix the other, or extract shared bootstrap.
- **Infinite-loop guard calls `alert()`** in `DomRenderer.ts:181`. Blocks the UI thread — and this is reachable, not theoretical: see the looping-story entry below, where it is what the "browser hangs" turns out to be. Prefer a silent console error + hard cap if you rewrite. (The equivalent guards in `core/state.ts` used to `alert()` too — they now just throw, keeping `core/` free of browser globals.)
- **A story that loops has three different failure modes, and which one you get is close to arbitrary.** The trigger is always a backwards `jump`. What decides the symptom is whether the loop contains a stop, and which of the four loop guards notices first. All three were reproduced and timed; none is currently handled.
  - **A loop with no stop in it, reached by the render loop** (`- label: top` / `- jump: top`). Nothing sets `stopAfterRender`, so `DomRenderer.render`'s auto-advance keeps advancing and re-rendering until `consecutiveCommands > 10000`, then alerts and throws `"Got stuck in infinite loop while rendering"`. Measured: the alert appears **437ms** after loading it in the player. The freeze people report is the `alert` blocking the UI thread, not the loop itself. Reached by the player booting, or the editor booting through `loadScript`.
  - **The same story, reached by a core replay instead**, throws `"Got stuck in infinite loop while replaying path"` in **2-8ms** with no alert and no freeze — an uncaught error in the console, leaving the editor half-updated. Routes in: `reloadStory` → `replayAsFarAsPossible` → `runToStop` (an editor blur), `goToCommandByReplay` (a replay jump), and `fromShorthandPath` (loading a save). Two of those three routes are recent, so a looping script now throws where it used to only alert. The message is the way to tell the two apart: *while rendering* against *while replaying path*.
  - **A loop that does contain stops, plus a replay jump to a command the loop never lands on**, fails silently and is the worst of the three. `goToCommandByReplay`'s no-progress check (`state.commandIndex === before`) only catches a loop with a single stop; with two or more the index alternates and never repeats, so the walk spins to `++steps > 10000` and **returns normally**. It records `path.advance()` every iteration, so the path ends up holding `Advance(10001)` — the cap plus one, since the advance is recorded before `steps` is tested. That path is garbage but perfectly valid: it replays, it serializes, and undo has to pop ten thousand advances one at a time. Reproduce with `label top` / `one` / `two` / `jump top` / `never reached` and a replay jump at the last command. `src/demoStory.ts` ends in `jump: loop` and has a second one on the good branch, so the demo reaches this.
  - Each wants a different fix. The silent one should treat hitting the cap as "target unreachable" and adopt neither the state nor the path, with the cap dropped to something proportionate like the command count — a reachable target is reached in a bounded walk. The throwing one wants catching at the editor boundary so a looping script is a message rather than an uncaught error. The alerting one is the entry above.
- **Loading a stale save can now throw, and nothing catches it.** Path replay fails loudly when a saved path doesn't match the story (`"Invalid decision id in saved path"`, `"Could not replay decision..."`) — deliberately, since silently diverging was worse. The hardcoded `"test"` id is gone (2026-08-29: the key is `vn-save-<id>` from the manifest), so two different stories no longer share one key — but the id names the project, not the version of its script, so a save made before an edit still loads afterwards, and `SaveLoadMenu` still calls `player.loadFromSlot` with no `try/catch`. A friendly "save is incompatible" message there is the missing piece. The symptom is not a crash screen: the click handler is a bare listener, so the throw skips `renderer.closeMenu()` and Load is simply a dead button.
- **Save/load confirmations are `window.confirm`.** All three prompts in `SaveLoadMenu` — overwrite, load, delete — are browser dialogs, and a browser dialog leaves fullscreen: on mobile the player is dropped out of fullscreen just by answering one. They want in-game dialogs instead, which is the same piece missing from the "save is incompatible" message above, and from the `alert()` two entries up.
- **`{and: <non-array>}` parses as vacuously true.** `getBoolExprList` in `booleanExpression.ts` returns `[]` for non-array input instead of a `ParserError`, so `{and: "oops"}` becomes `And([])` which evaluates `true` (and `{or: "oops"}` evaluates `false`). Should be a parse error.
- **Comparison operators don't type-check.** `["$name", "<", 5]` in a boolean expression does raw JS coercion, unlike the `set` command's arithmetic operators in `variables.ts` which throw on mixed types. Inconsistent; probably worth aligning.
- **`ConsecutiveIntegerSet.toJSON` returns its internal array by reference** (the `should deep clone..?` TODO is right). Callers currently `JSON.stringify` immediately so nothing breaks today, but holding onto the returned value and mutating the set will corrupt it.
- **Sub-renderers can write into an element a newer render already replaced.** `DomRenderer.render` stamps each pass with `renderGeneration` and its completion callback bails when superseded, but the sub-renderers themselves have no such guard. `TextBoxRenderer.renderAdv` clears the box, `await`s `renderAdvNameTag`, then appends the characters — and a non-animated render arriving in that gap swaps `this.advTextBox` for a fresh clone (that is how it cancels transitions and drops listeners). The stale pass resumes, re-reads the field, and appends into the *new* element, so the line renders twice ("ByeBye"). It only bites when the name tag is unchanged; when the speaker changes, the stale pass instead blocks forever on a `transitionend` for a detached element and never reaches the append. Not reachable from the UI today, because that `await` is a microtask and the browser drains microtasks before delivering the next click — real clicks, skip mode (50ms timer) and autoplay (7s interval) all resume the first pass before a second can start. It becomes reachable the moment a genuinely async step appears there. `advanceFast` in `test/demo/DemoStory.test.ts` deliberately spaces its two clicks a task apart for this reason — collapsing them into one turn used to reproduce the doubling.
  - **Half of it is closed as of 2026-08-29, and the half that is left is the one that needs the generation.** `renderAdv` now appends into the box it captured before its first `await` rather than re-reading the field, so a superseded pass writes into the element it started with — detached, and off screen. And it no longer awaits the name tag at all when `animate` is false: there is nothing to sequence when nothing animates, and awaiting an already settled promise was itself the microtask gap. An unanimated render is therefore atomic, which is what "jump straight to end-state" means everywhere else in this renderer. `test/browser/TextBoxRenderer.test.ts` covers that, by issuing the renders directly. What remains is **two animated passes suspended over the same box**: neither clones, so both can resume into it, and the capture does not help. That still wants the generation threaded into the sub-renderers and re-checked before every DOM write — and nothing exercises the capture until it is, so treat the capture as belt-and-braces rather than as covered.
